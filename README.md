# Speckled

**Don't Vibecode Yourself Into Oblivion**

Speckled is a spec-driven workflow that ensures your project (and it's source code) isn't pure slop. 

Use AI to help you plan and research before writing a single line of code. Approve every step with a record of every engineering decision made while using AI. Every feature moves through a chain of in-depth documents generated by role-specified agents, and a chosen human or humans approve each one before the next step can start.

Nothing gets built until the plan behind it has been written, reviewed and approved.

Why should you use Speckled?

- **Prompts are limited** - No matter how long or detailed, or multiple your prompt is, it ain't enough. Agents build from an approved brief, feature requirements, TDDs, designs and Eng tasks.
- **Human review.** - Humans approves both the approach and the code, always. Each PR is small, covers one task, and is checked against known acceptance criteria.
- **Trace it** - Every change traces back through task → design → requirement → roadmap, with who approved each step and when.
- **Plain files.** - Markdown docs live in a private planning repo next to your code, reviewed in your normal PR flow. As it should be.

## Install

Speckled is a [Claude Code](https://code.claude.com) plugin.

```bash
claude plugin marketplace add SpeckledAI/speckled
claude plugin install speckled@speckled
```

To try it for a single session without installing:

```bash
git clone https://github.com/SpeckledAI/speckled
claude --plugin-dir ./speckled
```

Every command is a slash command prefixed `/speckled:`. Type `/speckled` in a session to see them.

**Requirements:** Claude Code, git, and Python 3.9+ (for the hooks). Nothing else to install.

## Quickstart

In your code repo (new or existing):

```
/speckled:init
```

This asks for your project name, which code repos the project spans, your firm rules, who approves each step, and the enforcement mode. It creates a separate **planning repo** next to your code (`../<project>-plans` by default) holding `speckled.yaml` and the docs folders, so your plans stay private even if your code is public. It ends by printing the command that starts sessions from the planning repo:

```bash
cd ../<project>-plans && claude --add-dir ../<your code repo>
```

Run every Speckled command from there. Then follow the pipeline:

| # | You run | What happens | You then run |
|---|---|---|---|
| 1 | `/speckled:brief` | The analyst drafts the project brief with you | `/speckled:approve BRIEF` |
| 2 | `/speckled:pdrd` | The PM turns the brief into a phased roadmap of numbered features (F01, F02, …) | `/speckled:approve PDRD` |
| 3 | `/speckled:frd F01` | The PM writes testable requirements for feature F01 | `/speckled:approve FRD-F01` |
| 4 | `/speckled:tdd F01` | The architect designs it, using your real code | `/speckled:approve TDD-F01` |
| 5 | `/speckled:tasks F01` | The planner breaks the design into small, ordered tasks | `/speckled:approve TASKS-F01` |
| 6 | `/speckled:build` | The engineer implements the next ready task and hands it to you for review | `/speckled:approve T-F01-01` |

Repeat step 6 for each task, and steps 3–6 for each feature. Steps 1–2 happen once per project; after that the roadmap is revised as it changes.

**Existing codebase?** Run `/speckled:map` after `init` so the architect documents what already exists before designing anything new.

## How it works

### Approval gates

The first step in creating your app or software is in creating a brief. This is your starting point. The analyst agent drafts it with you from your own description of your idea, plus any notes, research or additions you share. 

If any part of the brief is incorrect or needs further refinement, work with the analyst to finalize the document. Once you appprove the brief you move on to the next step. Every later document is drafted by an AI agent in the same way. You work with AI agents to refine, and finalize requirement and technical documents before any code gets written and the code that does get written is also approved by you or a designated human 

Approved any document by running `/speckled:approve`.

(`ARCH`, the architecture document, is also a root: it's drafted from your existing code.)

```
Project Brief
  |
  |
PM agent writes Product Development Roadmap (PDRD) from brief.
  |
  | human approval
  |
PM agent write Feature Requirements Document (FRD) from PDRD
  |
  | human approval
  |
Architect agent writes Technical Design Document (TDD) from FRD
  |
  | human approval
  |
Planner agent writes Eng Tasks Document from TDD
  |
  | human approval
  |
You & Dev agent implement the code for each task in the Eng Tasks Document.
```

- **AI never approves.** - No agent may set a document to `approved`. `/speckled:approve` is disabled for the model; only humans can run it.
- **Agents draft from approved parents only.** - If the parent doc isn't approved, the agent stops and tells you. If you explicitly tell it to continue anyway, it adds a visible warning to the new document.
- **Editing reopens review.** - Changing an approved document sends it back to `in-review` and bumps its version, so a human can approve the change.
- **Out-of-date work gets flagged.** If a parent changes after a child was drafted from it, agents will point it out.

### Drafting with you

Every document-producing command works in one of two modes:

- **Guided (default).** The agent drafts one group of sections at a time, explains its choices and assumptions, lists its questions, and waits for your reply ("next", changes, or answers).
- **Draft-all.** Say "draft it all" and the agent writes the whole document in one pass, then lists every assumption and open question at the end.

Either way, assumptions are marked `**Assumption:**` inline, open questions go into the document (not only the chat), and progress is saved as you go. When a draft is complete, it is set to `in-review` and the agent tells you what most deserves your attention.

### Firm rules (constraints)

Declare the rules your product must never break in `speckled.yaml` (for example, "strict validation in all form fields" or "no personal data in logs"). Every FRD, TDD and task list ends with a **Constraints Check** that shows how it respects each one. Agents never quietly weaken a constraint; a design that needs an exception records it as an open question for you.

## Command reference

### Setup

#### `/speckled:init`
Sets up Speckled in a project.
- Asks for: project name, planning repo path (default `../<project>-plans`), docs directory (default `docs`), code repos, constraints, approvers per gate, and the enforcement mode (`off`, `warn` or `block`; it suggests `warn`).
- Creates the planning repo with `git init`, writes `speckled.yaml` there (`repos` lists code repos only), and creates `<docs>/research`, `frds`, `tdds` and `tasks`. Never overwrites existing files.
- With enforcement on, installs the commit-time notice in the planning repo (`speckled-gate install-git-hook`).
- On an existing codebase, offers to run `/speckled:map` and summarizes any existing docs it finds.
- Ends by printing the command that starts sessions from the planning repo.
- Run in an existing planning repo, it shows `speckled.yaml` and asks what to change. It never creates a second planning repo.

#### `/speckled:map`
Writes or refreshes `ARCH`, the **current-state** architecture document: what actually exists, including technical debt.
- Role: architect.
- Reads: every repo in `speckled.yaml` (structure, manifests and lockfiles, entry points, config, CI, tests, schemas, integrations), and asks you about things the code doesn't show.
- Writes: `<docs>/architecture.md`. If it already exists, it is updated in place and the change is logged.
- Tip: on large codebases, tell it which areas to focus on.

### Planning

#### `/speckled:brief`
Drafts the project brief: problem, target users, solution, goals and metrics, MVP scope, business model, competitors, constraints, risks.
- Role: analyst. Pushes back on vague problems, unmeasurable goals and oversized MVPs.
- Writes: `<docs>/brief.md` (`BRIEF`).
- Offers to copy the brief's constraints into `speckled.yaml`.
- Next: `/speckled:approve BRIEF`, then `/speckled:pdrd`.

#### `/speckled:research [topic]`
Market or competitor research, or a research plan for deeper investigation.
- Role: analyst.
- Asks which output you want: **research now** (uses web search, cites every source), or a **research plan** (a self-contained prompt for a deep-research tool or a human researcher).
- Writes: `<docs>/research/<slug>.md`, or `<slug>-plan.md` for a plan.

#### `/speckled:pdrd`
Drafts or revises the **PDRD** (Product Development Roadmap Document), the project's source of truth for scope: goals, principles, phases, numbered features, out-of-scope items, risks, open questions.
- Role: product manager. Parent: `BRIEF` (must be approved).
- New PDRD: agrees the phases with you first, then writes features phase by phase.
- Revision: keeps every existing feature ID; new features get the next unused number; cut or deferred features keep their ID with a status. Lists which FRDs, TDDs and task lists the change affects.
- Writes: `<docs>/pdrd.md` (`PDRD`).
- Next: `/speckled:frd <feature id>`.

#### `/speckled:frd <feature id>`
Writes a **Feature Requirements Document** for one PDRD feature: user stories, numbered requirements (`FR1`, `NFR1`, …), UX, data, security and compliance, success metrics, scope, acceptance criteria, open questions.
- Role: product manager. Parent: `PDRD` (must be approved).
- Without an argument, lists features that don't have an FRD yet, in phase order.
- `frd`, `tdd` and `tasks` accept a feature ID (`F07`) or any of its document IDs (`FRD-F07`).
- Warns if features this one depends on aren't done or approved yet.
- Writes: `<docs>/frds/F07-<slug>.md` (`FRD-F07`).
- Next: `/speckled:tdd F07`.

#### `/speckled:tdd <feature id>`
Writes a **Technical Design Document**: current state, design and alternatives, data model, interfaces, frontend, security, reliability and performance, testing, rollout, and a table tracing every requirement to the design.
- Role: architect. Parent: `FRD-F07` (must be approved).
- Without an argument, lists approved FRDs that don't have a TDD yet.
- Reads the FRD, `ARCH`, the PDRD entry and **the actual code** the feature touches.
- If `ARCH` is missing or older than recent code changes, recommends `/speckled:map` first.
- Writes: `<docs>/tdds/F07-<slug>.md` (`TDD-F07`).
- Next: `/speckled:tasks F07`.

#### `/speckled:tasks <feature id>`
Breaks an approved TDD into small, dependency-ordered development tasks. Each task has context, exact steps, tests, acceptance criteria, and the TDD sections and requirements it implements.
- Role: planner (never modifies code). Parent: `TDD-F07` (must be approved).
- Without an argument, lists approved TDDs that don't have a task list yet.
- Tasks are numbered in dependency order (`T-F07-01`, `T-F07-02`, …), sized to be reviewed in one sitting, with backend, frontend and integration work kept separate. Work only a person can do (creating accounts, buying services) is assigned to a human.
- Includes a coverage table showing that every TDD section maps to at least one task.
- Writes: `<docs>/tasks/F07-<slug>.md` (`TASKS-F07`).
- Next: `/speckled:build T-F07-01`.

### Building

#### `/speckled:build [task id]`

Prompts the Dev agent to implement an approved task with you, then hands it over to you for review.

1. Without an argument, shows the next tasks whose dependencies are done and asks which one.
2. Checks the gate: the task list must be approved and every task this one depends on must be done. Otherwise it stops and explains what's blocking it.
3. **Activates the task:** sets it to `In progress` and runs `speckled-gate activate <task id>`, which checks in code that the task can be worked on: its list can be read and is approved, the task is `In progress` or `In review`, and every task it depends on exists and is done. If all checks pass, it records the task as your active task. If any check fails, it reports why and stops. These are the same checks every code edit gets while enforcement is on.
4. Reads the task, the TDD and FRD sections it cites, and the code it touches. Asks before writing code if anything is unclear.
5. Implements within the task's scope, writes the specified tests, and runs lint and tests.
6. Sets the task to `In review` (never `Done`) and hands it over: what changed and why, how it was tested, any deviations, open questions, and a suggested commit message containing the task ID.

**Why activate a task?** A tool call doesn't say which task a change is for, so the active task is how Speckled connects code changes to an approved plan. When `enforcement` is on in `speckled.yaml`, every code edit is checked against it: the task's list must be approved, the task `In progress` or `In review`, and its dependencies done. Once the task is `Done`, further edits are blocked until the next task is activated. The active task is stored in `.speckled/active-task` in the planning repo, per developer (it's git-ignored), and only `speckled-gate activate` can set it. Check it at any time with `speckled-gate status`.

Next: review the change, then `/speckled:approve T-F07-01`.

#### `/speckled:review [target]`
An architect review of code or a document against the approved specs.
- Target: a task ID, file, diff range or document ID. Defaults to the uncommitted diff.
- Checks, ranked by severity: correctness against the task, TDD and FRD (and nothing outside their scope), constraints, security, reliability and performance, fit with existing patterns, and whether the tests verify the acceptance criteria.
- Each finding has a location, a concrete failure scenario and a suggested fix. It doesn't change anything unless you ask.

#### `/speckled:explain [what]`
Explains the last change (or anything you name) as if teaching a junior engineer: what changed, step by step with file references; why, citing requirement and task IDs; alternatives considered; the concepts needed to understand it; risks and how to verify.

#### `/speckled:pair [topic]`
Pair-programming mode for debugging, exploration, spikes or design discussion. Small steps, thinking out loud, numbered options. If the session turns into feature work, it suggests capturing that as a task so it goes through review.

### Approving

#### `/speckled:approve <id> [note]`
Records **your** approval. Only you can run it; it is disabled for the model.
- Targets: `BRIEF`, `PDRD`, `ARCH`, `FRD-F07`, `TDD-F07`, `TASKS-F07`, or a task such as `T-F07-03`. Without an argument, lists everything that's `in-review`.
- Uses your `git config user.name` as the approver, and warns if you aren't listed for that gate in `speckled.yaml`.
- Before recording, points out anything that should block approval: the document isn't `in-review`, the parent isn't approved or has changed since, open questions are unanswered, or the Constraints Check is empty. You confirm.
- **For a document:** sets `status: approved` and adds `{by, role, date, version, note}` to its `approvals` list.
- **For a task:** sets the task to `Done` and adds "Approved by … on …". When every task in a list is done, it offers to mark the list done and move the feature's documents to `completed/`.

### Specialist

#### `/speckled:design [feature or asset]`
Designs visual or motion assets (icons, illustrations, UI graphics, animation) for a feature, based on the FRD's UX section and your brand material, and optionally implements them in the frontend.

#### `/speckled:localize`
Finds UI text that hasn't been translated and adds translations for the languages your app **already** supports, following your existing i18n setup. Flags translations it's unsure of, and lists i18n problems it notices.

## Agents

The pipeline steps run in your main session, so they can stop and talk to you. The six roles are also available as subagents (`speckled:analyst`, `speckled:pm`, `speckled:architect`, `speckled:planner`, `speckled:dev`, `speckled:designer`) for work that doesn't need back-and-forth, such as asking the architect to review a branch in the background or the pm to re-think a feature.

| Role | Owns | Never does |
|---|---|---|
| **analyst** | Brief, research | Roadmaps, requirements, designs, code |
| **pm** | PDRD, FRDs | Framework or schema choices, tasks, code |
| **architect** | `ARCH`, TDDs, architecture reviews | Product scope changes, feature implementation |
| **planner** | Task lists | Application code, scope beyond the TDD |
| **dev** | Code for one approved task at a time | Changes to requirements or designs; marking tasks done |
| **designer** | Visual and motion assets | Product scope changes |

No agent ever approves anything.

## Configuration: `speckled.yaml`

Created by `/speckled:init` at the root of the planning repo:

```yaml
project: Acme Payments
docs_dir: docs              # where Speckled documents live, inside the planning repo
enforcement: warn           # off | warn | block (missing means off)
enforcement_exempt:         # optional: files any task may change, relative to each code repo
  - "*.lock"
repos:                      # the code repos this project spans; agents read all of them
  - ../acme-web
  - ../acme-api
  - ../acme-mobile
constraints:                # firm rules; every FRD, TDD and task list must respect them
  - id: C1
    rule: Every payment requires explicit user confirmation.
  - id: C2
    rule: No personal data in logs or queue payloads.
roles:                      # who may approve each gate (git user names)
  brief: [alice]
  pdrd: [alice]
  frd: [alice, bob]
  tdd: [carol]
  tasks: [carol]
  code: [bob, carol]
```

A solo developer can list themselves for every gate.

### The planning repo

Speckled keeps plans in their own git repo next to your code repos, never inside them. Your plans stay private even if your code is public, and one set of plans can cover several code repos. `repos` lists only the code repos, as paths relative to the planning repo. Start every session in the planning repo, adding each code repo:

```bash
cd ~/code/acme-plans && claude --add-dir ../acme-web --add-dir ../acme-api
```

### Enforcement

`enforcement` decides whether the approval gates are also checked in code, by a hook that runs before each tool call:

- **`off`** (or missing): nothing is checked. Gates are followed through the agents' instructions only.
- **`warn`** (what `/speckled:init` suggests): agents work freely. A code change outside an approved task goes ahead, but the agent is told and the change is logged in `.speckled/log.jsonl`.
- **`block`**: the same, but agent code changes outside an approved task are also stopped, with a message saying what to do next.

With enforcement on, in either mode:
- Agents can't change the gate's own controls: `speckled.yaml`, `.speckled/`, git hooks, Claude Code settings files, or the plugin.
- Agents can't commit, push or open pull requests.
- Every block is logged in `.speckled/log.jsonl`.
- Planning documents stay free to edit, and your own edits are never checked.

In `block` mode, changing code in a listed repo also needs an **active task** (set by `/speckled:build`): its task list approved, the task `In progress` or `In review`, and every task it depends on done.

`enforcement_exempt` lists patterns (Python `fnmatch`, where `*` also matches `/`) for code-repo files any task may change. Only you can change these settings: agents can't edit `speckled.yaml` while enforcement is on. The full rules are in [`protocol/documents.md` §8](protocol/documents.md).

## Documents, IDs and statuses

### Layout

```
<docs_dir>/
  brief.md          BRIEF
  research/         market and competitor research
  pdrd.md           PDRD, the roadmap and source of truth for scope
  architecture.md   ARCH, the current-state architecture
  frds/             FRD-F07   → frds/F07-<slug>.md
  tdds/             TDD-F07   → tdds/F07-<slug>.md
  tasks/            TASKS-F07 → tasks/F07-<slug>.md
```

When a feature's work is finished, its documents move to a `completed/` subfolder next to where they live. They're kept as history, never deleted or renumbered.

### IDs

| ID | Meaning |
|---|---|
| `F07` | A feature in the PDRD. **Permanent:** never renumbered or reused, even if the feature moves phase or is cut |
| `FRD-F07`, `TDD-F07`, `TASKS-F07` | The documents for feature F07 |
| `T-F07-03` | The third task for F07, in dependency order |
| `FRD-F07/FR3` | Requirement FR3 in FRD-F07 |

Carry IDs into your work so everything can be traced: commit messages and PR titles reference the task (`feat(scanner): add universe filter [T-F07-03]`), and comments that explain why code exists cite the requirement (`// FRD-F07/FR3`).

### Front matter

Every document starts with:

```yaml
---
id: TDD-F07
title: Market Scanning
type: tdd                # brief | research | pdrd | arch | frd | tdd | tasks
feature: F07
parent: FRD-F07          # the approved document this was drafted from
parent_version: 2        # the parent's version at drafting time
status: in-review        # draft | in-review | approved | done | superseded
version: 1
updated: 2026-10-01
approvals: []            # written only by /speckled:approve
---
```

### Statuses

| Status | Meaning | Set by |
|---|---|---|
| `draft` | Being written | Agent |
| `in-review` | Ready for a human decision | Agent, at hand-off |
| `approved` | A human approved this version | `/speckled:approve` only |
| `done` | Its work is complete | `/speckled:approve` only |
| `superseded` | Replaced by a newer document | Agent, at your request |

Tasks inside a task list use `Todo` → `In progress` → `In review` → `Done`. Only `/speckled:approve` sets `Done`.

## Approvals

Approvals are entries in each document's front matter:

```yaml
approvals:
  - {by: alice, role: frd, date: 2026-10-01, version: 1, note: "OK to defer FR6"}
  - {by: alice, role: frd, date: 2026-10-08, version: 2}
```

Each entry records who approved which version. When an approved document is edited, earlier entries stay, so the history shows every version that was approved.

**On a team:** the documents are Markdown in git, so review FRDs and TDDs as ordinary pull requests. Discuss in the PR, and have the approver run `/speckled:approve` before merging.

## Checking the record: `lint-chain`

`lint-chain` checks that the planning repo's record holds together: every document is well-formed, every document was drafted from an approved parent, every approval was made by someone allowed to make it, and nothing approved was quietly changed later. It reads the documents and the repo's git history, and reports what it finds. It changes nothing and blocks nothing.

**What it checks:**

| Group | Rules |
|---|---|
| **Structure:** front matter, IDs, file names, features and the task format | `front-matter`, `bad-id`, `duplicate-id`, `file-name`, `unknown-feature`, `task-format`, `duplicate-task`, `dependency-missing`, `dependency-cycle` |
| **Chain:** each document's parent exists, is the right kind and was approved | `parent-missing`, `parent-wrong-type`, `parent-unapproved`, `parent-reopened` |
| **Approvals:** approvers are listed under `roles` in `speckled.yaml`, for the right gate | `approver-not-listed`, `approval-role-mismatch`, `gate-without-approvers` |
| **History:** approvals are only ever added, documents are moved rather than deleted, and approved documents aren't edited without a new review | `approval-edited`, `approval-removed`, `document-deleted`, `edited-without-review`, `history-unavailable` |
| **Log:** `.speckled/log.jsonl` is only ever appended to, and every line is valid | `log-edited`, `log-malformed`, `warn-event` |

Each rule's meaning and severity are in [`protocol/documents.md` §9](protocol/documents.md), and `lint-chain --explain <rule>` prints them with how to fix it.

**Running it:** run it from the planning repo. It's in the plugin's `bin/` folder; with a clone of this repo next to your planning repo:

```bash
../speckled/bin/lint-chain                  # everything, as text
../speckled/bin/lint-chain --docs           # only the checks that need no git history (fast)
../speckled/bin/lint-chain --feature F07    # only one feature's documents and tasks
../speckled/bin/lint-chain --json           # the report as JSON (--output FILE also writes it to a file)
../speckled/bin/lint-chain --strict         # warnings fail the run too
../speckled/bin/lint-chain --explain edited-without-review
```

Reports name rules, IDs, file paths and lines, commits, approver names and dates. They never quote titles or document text, and never contain email addresses, so they can be shared or kept as CI artifacts.

**Exit codes:**

| Code | Meaning |
|---|---|
| `0` | No errors. Warnings don't count unless `--strict` is set. |
| `1` | At least one error, or with `--strict`, any finding. |
| `2` | It couldn't run: no `speckled.yaml`, an unreadable configuration, or a git failure. |
| `64` | A usage error, such as an unknown option or a malformed `--feature`. |

**In CI:** the [`lint-chain` GitHub Action](actions/lint-chain/README.md) runs it on every push and pull request to the planning repo and writes the report to the job summary. It needs the full history (`fetch-depth: 0`), because a shallow clone can't show whether approvals were changed.

**What it can't tell you:**
- **Approver names aren't verified.** An approval passes if its name is listed under `roles`, and the name comes from `git config user.name`, which anyone can set. Signed approvals aren't checked yet.
- **Rewritten history can't be detected locally.** If someone rewrites the repo's history (a force-push or a rebase that edits old commits), the rewritten history is all `lint-chain` sees, and it may look clean. Protect the planning repo's main branch against force-pushes.

## Common workflows

**New project:** `init` → `brief` → `pdrd` → for each feature: `frd` → `tdd` → `tasks` → `build` …, with `approve` after every step.

**Existing codebase:** `init` → `map` → write a short brief of where the product is going → `pdrd` (record existing capabilities as features with status Done) → continue per feature.

**Multi-repo project:** list every code repo under `repos` in `speckled.yaml`, and add each one when you start a session (`--add-dir`). `map`, `tdd`, `tasks` and `build` read all of them, and each task names the repo it touches.

**Scope change:** run `/speckled:pdrd` and describe the change. Existing feature IDs are kept, new features get the next number, and the agent lists which FRDs, TDDs and task lists are affected. Approve the revised PDRD, then revise the affected documents.

**A task turns out to be wrong:** stop `build`, describe the problem, and fix it at the right level: the task list (`/speckled:tasks`), the design (`/speckled:tdd`) or the requirements (`/speckled:frd`). The edited document goes back to `in-review` for your approval.

**Learning as you go:** after any `build`, run `/speckled:explain`.

## Troubleshooting

**"Run `/speckled:init`" / `speckled.yaml` missing.** Every command reads `speckled.yaml` first. Start the session in your planning repo, or run `/speckled:init` from your code repo to create one.

**The agent won't draft: "parent not approved".** That's a gate working as intended. Approve the parent with `/speckled:approve <id>`, or tell the agent explicitly to continue; it will add a visible warning to the new document.

**Claude says it can't run `/speckled:approve`.** By design: approval is a human action. Type the command yourself.

**"Not a listed approver" warning.** Your `git config user.name` isn't listed for that gate under `roles` in `speckled.yaml`. Fix the name or the roles list, or confirm to continue.

**A command was blocked by `speckled guard`.** The safety hook blocks recursive forced deletes (`rm -rf`) and access to secret `.env` files. Delete specific paths instead, or run the command yourself in your terminal.

**A change was blocked (or warned about) by `speckled`.** With enforcement on, each message names what's wrong and the next step. Blocks start with `speckled: blocked:`. In `warn` mode, a code change outside an approved task starts with `speckled (warn): would block:` and still goes ahead. The gate's own controls, commits, pushes, pull requests and an unreadable config are blocked in both modes, and their message doesn't suggest `warn`, which wouldn't help. Every block and warning is logged. By rule:

| Rule | What it means | What to do |
|---|---|---|
| `no-active-task` | No task is active, or the active task isn't in any task list. | Run `/speckled:build <task id>` for a ready task. |
| `task-not-started` | The active task is still `Todo`. | Run `/speckled:build <task id>`, which starts it. |
| `task-done` | The active task is already `Done`. | Start the next task with `/speckled:build`. |
| `task-list-not-approved` | The task's list isn't approved. | Review it and run `/speckled:approve TASKS-F07`. |
| `dependency-not-done` | A task this one depends on isn't done. | Finish and approve that task first. |
| `dependency-missing` | A `Depends on` entry isn't in any task list. | Fix the `Depends on` line. |
| `protected-path` | The agent tried to change the gate's own controls (`speckled.yaml`, `.speckled/`, git hooks, settings, the plugin). | Make the change yourself. |
| `hooks-disabled-session` | The agent tried to start a session with hooks off. | Run it yourself if you meant to. |
| `git-commit`, `git-push`, `pull-request` | Agents don't commit, push or open PRs. | Review the diff and commit yourself. |
| `wrong-start-folder` | The session started in a code repo. | Restart from the planning repo; the message prints the command. |
| `config-unreadable` | `speckled.yaml` or a task list can't be read. | Fix the file the message names. |

`speckled-gate status` (in the plugin's `bin/`) shows what the gate sees: the mode, the active task and whether it's valid. To relax the gate, set `enforcement: warn` in `speckled.yaml`, or `enforcement: off` to switch it off. Edit the file yourself: agents can't change it while enforcement is on.

**Out-of-date warnings.** A parent document changed after this one was drafted from it. Check whether the change affects this document; revise it if so, and approve again.

## Limitations

Speckled is early (v0.4). In particular:

- **Enforcement is a guardrail, not a security boundary.** With `enforcement` on, the hook checks the agent's file edits, the shell commands it recognises, commits, pushes and pull requests. It doesn't stop a human, or any process outside the agent, from editing files, changing settings or switching the plugin off. Shell commands that write files in ways it doesn't recognise (for example a script that generates code) can get through. A server-side check on pull requests is planned.
- **Approvals aren't blocked at the hook.** An agent could still write an approval entry into a document. It can't commit it, and the commit-time notice lists every approval in a commit, so review the diff before you commit.
- **The approver's identity is `git config user.name`**, which anyone can set. Treat approvals as a team record, not a security control, until verified approvals ship. `lint-chain` can't detect rewritten git history either (see [Checking the record](#checking-the-record-lint-chain)).
- **A change to the PDRD flags every FRD as out of date**, not only the affected ones. Roadmap amendments and per-feature versioning (F37) will fix this.
- **The templates are part of the plugin.** To customize them today, fork the plugin.
- **Claude Code only** for now. Adapters for other coding agents are on the roadmap.

## What this plugin runs

Speckled is mostly instructions: Markdown agents, skills, templates and protocol files that Claude reads. The code it runs is Python 3.9+, uses only the standard library plus a bundled copy of PyYAML, and makes no network calls. All of it runs **locally**:

- **`hooks/pretooluse.py`**, the one `PreToolUse` hook. It runs both checks below in a single process before each Bash, PowerShell, Read, Edit, MultiEdit, Write, NotebookEdit, Grep, Glob and MCP tool call: the guard first, then, if the guard allows the call and it can change something, the gate.
- **`hooks/guard.py`**, the safety guard. It blocks recursive forced deletes (`rm -rf` and equivalents, including through `bash -c`, `xargs` and `find -delete`) and access to secret `.env` files (`.env.example`, `.env.sample`, `.env.template` and `.env.dist` stay allowed). It runs whether or not enforcement is on. With enforcement on, it records each block in the gate's log below (as `recursive-delete` or `secret-env-file`, never with the command text); otherwise it writes nothing.
- **`hooks/gate.py`**, the gate, which enforces the approvals (see [Enforcement](#enforcement)). It doesn't run for Read, Grep and Glob. With `enforcement` off or missing it does nothing. It writes:
  - `.speckled/log.jsonl` in the planning repo: one line per action allowed in `warn` mode and per block, in either mode, with the outcome, the time, your `git config user.name`, the tool, the file paths, the task and the rule. Never file contents, commands or email addresses. It's meant to be committed.
  - `projects.json` in the plugin's data folder (on this machine only): which planning repo each code repo belongs to.
- **`bin/speckled-gate`**, the gate's command line: `activate` (run by `/speckled:build`) writes the per-developer, git-ignored `.speckled/active-task`; `check` and `status` only read; `install-git-hook` copies the commit-time notice into the planning repo.
- **`bin/lint-chain`**, which checks the planning repo's record (see [Checking the record](#checking-the-record-lint-chain)). It only runs when you or your CI run it. It reads the planning repo and its git history, writes nothing except the file you name with `--output`, and blocks nothing.
- **`hooks/pre-commit-notice.py`**, the optional commit-time notice, installed as the planning repo's `.git/hooks/pre-commit`. When you commit, it lists the approvals and status changes in the commit. It never blocks a commit. It's never installed over an existing hook; you're shown the line to add instead.

Speckled sends no data anywhere, and doesn't change your Claude Code settings or permissions. The documents it creates are plain Markdown files in your planning repository.
